Session lanes for Claude Code

One queue file per repo, four commands that each open a different kind of session, and one command that closes it. Every session starts knowing what to do, and several can run at once.

The idea

Most AI coding sessions start from a blank prompt and end with the context lost in chat history. This kit replaces both ends with files in the repo:

  • QUEUE.md holds every piece of pending work, sorted into lanes by kind of work.
  • An opener command (/queue:build, /queue:spec, /queue:meta, /queue:audit) starts a session by reading one lane.
  • /queue:end closes the session: it updates the queue, writes a handoff note for the next session, and commits.

The lanes exist because the four kinds of work need different behaviour. A build session should build and never stop to redesign. A spec session should make decisions and write them down. Mixing them is how a session spends an hour planning when it was opened to ship.

A typical run

Here is how a normal stretch of work looks: six sessions in a row, one of them split across two terminals. Each box is one session. Every session opens with one command and closes with /queue:end; then /clear (or a fresh terminal) starts the next one with an empty context. The queue file carries everything forward, so nothing has to be re-explained.

  1. /queue:spec turns ideas and open questions into concrete Build rows, packed into Session groups.
  2. /queue:build builds the first group. Its /queue:end says what comes next.
  3. Two builds at once. When /queue:end prints Next: /queue:build ×2 (files disjoint), open a second terminal and type /queue:build in both. Each one claims a different group, and the two never touch the same files.
  4. /queue:spec again once the planned rows run low: it picks up what the builds learned and writes the next rows.
  5. /queue:build works through those rows.
  6. /queue:audit closes the stretch: it checks that the README and docs still match what was just built, and queues any gaps.

How to pick the next session

You rarely have to think about it: read the Next: line that /queue:end prints and follow this.

The sections below explain each piece: the queue file, what each opener does, and how parallel terminals stay out of each other's way.

QUEUE.md

One file, fixed location: Documentation/planning/QUEUE.md, or QUEUE.md at the repo root. Every command looks in those two places, in that order.

## ▶ NEXT SESSION — START HERE    ← handoff note, rewritten by /queue:end
## Settled                        ← dated decisions, append-only
## Inbox                          ← raw ideas; anyone adds, /queue:spec sorts them into rows
## Build                          ← concrete steps, packed in "Session N" groups → /queue:build
## Spec                           ← open decisions   → /queue:spec
## Meta                           ← process friction → /queue:meta
## Audit                          ← claims to verify → /queue:audit

A Build row

- [HEAD] Build 7 — Parse the export header into a typed record
  - Files: src/parser.py, tests/test_parser.py
  - Guardrails: header order varies by vendor; match on names, never position
  - Done when: pytest tests/test_parser.py passes on all three sample files
  • [HEAD] marks the one row /queue:build takes next. /queue:end moves it down once the gate passes.
  • Guardrails names the condition to hold so the work lands right: the thing a reader of the one-line summary would miss.
  • Done when is an observable check, so "finished" is a fact, never a feeling.
  • Finished rows are deleted. The commit message is the record.
  • /queue:spec packs rows into Session groups (**Session 3 — packed by file:** Files ...). A group is one terminal's work. Groups with no files in common can be built at the same time.

The four openers

/queue:build

"Make the next thing."

  • Claims one unheld Session group in its own git worktree
  • Builds each row to its Done-when gate, commits, moves on
  • Never re-plans; a design gap becomes a Spec row
  • Can fan a parallel wave out to subagents

/queue:spec

"Decide, then write it down."

  • Sorts ## Inbox into rows (the only lane that does)
  • Takes an open decision from ## Spec
  • Researches, decides, records it in ## Settled
  • Writes concrete rows into ## Build
  • Groups file-disjoint rows into parallel waves

/queue:meta

"Fix how we work."

  • Takes friction from ## Meta
  • Fixes commands, conventions, scripts, hooks
  • Fixes a problem at the highest level that governs it
  • Hands back to /queue:build quickly

/queue:audit

"Is what we wrote true?"

  • Takes a claim from ## Audit
  • Checks the docs against the code and the numbers
  • Fixes cheap gaps on the spot
  • Queues the rest into the right lane

Where to fix a problem: CLAUDE.md > QUEUE.md > /queue:meta > /queue:audit > /queue:spec > /queue:build. A wrong rule high up silently corrupts everything below it, so fix it where it lives. Then come straight back down: /queue:build is the point of the other five.

The lane is named Spec rather than Plan because /plan is already a built-in Claude Code command.

Parallel sessions

Each opener starts by creating its own git worktree: a second checkout of the same repo on its own branch, in a folder under .claude/worktrees/. The worktree name is the claim (build-s3-20261020). Two worktrees cannot share a name, so two terminals never take the same work. At /queue:end the session rebases its branch and fast-forwards it into the main branch.

Below: four terminals on one repo in one afternoon. Two build different Session groups, one audits, one specs, and one build session fans a parallel wave out to three subagents.

Which sessions run well side by side

PairFitWhy
/queue:build + /queue:buildGoodWhen their Session groups share no files. /queue:end tells you how many: Next: /queue:build ×2 — Sessions 3 and 4 (files disjoint). Open that many terminals and type /queue:build in each; each claims the next free group.
/queue:build + /queue:auditGoodCode versus docs. Audit queues fixes rather than editing code a build holds.
/queue:build + /queue:specGoodSpec puts new rows into a new group when an existing one is held, and leaves the held group's text alone.
/queue:spec + /queue:specPlan itBoth sort the Inbox and repack groups. One spec session at a time is simpler.
/queue:meta + anythingPlan itMeta edits the commands the other sessions run. A changed command takes effect in the next session, so finish in-flight work before relying on it.

Rules that keep parallel safe

  • One worktree per session. Never open a second session inside an existing worktree folder. The opener creates its own, and backs out if the name was already taken.
  • Session groups are the file split. /queue:spec packs rows so each group owns its files. A group whose files overlap a held group counts as held.
  • QUEUE.md is the one shared file. On a rebase conflict, keep both sessions' rows and both handoff blocks (newest first); the next /queue:end folds them together. ## Settled is append-only, so keep both lines.
  • Stage and commit explicit paths. git commit -m "..." -- src/parser.py. Avoid git add ., git commit -a, and a bare git commit, which takes whatever is already staged.
  • Commit small, land at /queue:end. Rebase onto the default branch, push the session branch, open a pull request, remove the worktree; a person merges it. A repo with Land: push in its /end in this repo section fast-forward merges and pushes instead; if the fast-forward refuses because another session merged first, rebase again.

Get started

# 1. install the plugins (architect-crew is optional)
/plugin marketplace add Strong-Force-Analytics/claude-plugins
/plugin install queue@sfa-plugins
/plugin install architect-crew@sfa-plugins

# 2. seed a repo
mkdir -p Documentation/planning
cp templates/QUEUE.md Documentation/planning/QUEUE.md
echo ".claude/worktrees/" >> .gitignore   # session worktrees live here

# 3. in Claude Code, inside that repo
/queue:spec     # turn your first idea into Build rows
/queue:build    # build the [HEAD] row
/queue:end      # wrap: update the queue, commit, open the pull request

Day to day: drop ideas into ## Inbox whenever they occur to you; the next /queue:spec sorts them into rows. Open whichever lane fits the time you have.
